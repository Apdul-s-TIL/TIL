# Kubernetes Architecture

## Cluster Architecture

![쿠버네티스 클러스터 아키텍처](./images/kubernetes-cluster-architecture.svg)

- 쿠버네티스 클러스터는 **컨트롤 플레인(Control Plane)**과 컨테이너화된 애플리케이션을 실행하는 **워커 머신(Worker machines)**들의 집합인 **노드(Nodes)**로 구성됨
- 모든 클러스터는 파드(Pods)를 실행하기 위해 최소 하나 이상의 워커 노드가 필요함
- 워커 노드는 애플리케이션 워크로드의 구성 요소인 파드(Pods)를 호스팅 함
- 컨트롤 플레인은 클러스터 내의 워커 노드와 파드를 관리함
- 운영(Production) 환경에서 컨트롤 플레인은 보통 여러 대의 컴퓨터에서 실행됨
- 클러스터는 일반적으로 여러 개의 노드를 운영함으로써 장애 허용성(Fault-tolerance)와 고가용성(High availability)을 제공함
- 위 다이어그램은 쿠버네티스 클러스터에 대한 예시 아키텍처를 나타냄
    - 각 노드는 `kube-proxy` 컴포넌트를 실행함
        - 클러스터 네트워크에서 서비스 API와 관련 동작을 사용할 수 있도록 각 노드에는 네트워크 프록시 컴포넌트가 필요함
        - 만약 자체 서드파티 프록시 구현을 제공하는 네트워크 플러그인을 사용하면, 노드에 `kube-proxy`를 실행할 필요가 없음

## Control plane components

- 컨트롤 플레인의 컴포넌트는 클러스터에 대한 전역적인 의사결정(e.g. 스케줄링)뿐만 아니라, 클러스터의 이벤트(e.g. 디플로이먼트의 `replicas` 필드 조건이 충족되지 않을 때 새로운 파드를 시작하는 것)를 감지하고 대응함
- 컨트롤 플레인 컴포넌트는 클러스터 안의 어떤 머신에서도 실행될 수 있음
    - 하지만 설정을 단순화하기 위해 일반적으로 설치 스크립트는 모든 컨트롤 플레인 컴포넌트를 동일한 머신에서 시작함
    - 해당 머신에서는 사용자 컨테이너를 실행하지 않음

### kube-apiserver

- API 서버는 쿠버네티스 API를 외부에 노출하는 쿠버네티스 컨트롤 플레인의 컴포넌트
    - API 서버는 쿠버네티스 컨트롤 플레인의 프론트 엔드 역할을 함
- `kube-apiserver`는 쿠버네티스 API 서버의 주요 구현체임
    - `kube-apiserver`는 수평적으로 확장 가능하도록 설계되었음
    - 즉, 인스턴스를 추가로 배포하여 확장할 수 있음
    - 여러 개의 `kube-apiserver` 인스턴스를 실행하고, 인스턴스 간의 트래픽을 분산시켜 운영할 수 있음

### etcd

- 모든 클러스터 데이터를 담는 쿠버네티스 뒷단 저장소(Backing store)로 사용되는, 일관성과 고가용성을 보장하는 키-값(Key-Value) 저장소
- 쿠버네티스 클러스터에서 `etcd`를 뒷단 저장소로 사용한다면, 해당 데이터에 대한 백업 계획이 반드시 마련되어야 함

### kube-scheduler

- 노드가 할당되지 않은 새로 생성된 **파드(Pods)**를 감지하여, 해당 파드가 실행될 적절한 노드를 선택해 주는 컨트롤 플레인 컴포넌트
- 스케줄링 의사결정을 위해 고려되는 요소들은 다음과 같음:
    - 리소스에 대한 개별 및 총체적 요구 사항
    - 하드웨어/소프트웨어/정책적 제약
    - 어피니티(Affinity) 및 안티-어피니티(Anti-affinity) 명세
    - 데이터 지역성(Locality)
    - 워크로드 간 간섭
    - 데드라인(Deadlines)

### kube-controller-manager

- 컨트롤러 프로세스를 실행하는 컨트롤 플레인 컴포넌트
- 논리적으로 각 컨트롤러는 별개의 프로세스이지만, 복잡성을 낮추기 위해 모두 단일 바이너리로 컴파일되어 단일 프로세스 내에서 실행됨
- 컨트롤러에는 여러 가지 유형이 있음
    - 다음과 같은 대표적인 예시가 있음
        - 노드 컨트롤러(Node controller): 노드가 다운될 때, 이를 감지하고 대응함
        - 잡 컨트롤러(Job Controller): 일회성 작업을 나타내는 잡(Job) 오브젝트를 감시하고, 해당 작업을 수행하기 위한 파드를 생성함
        - 엔드포인트슬라이스 컨트롤러(EndpointSlice controller): 서비스(Service)와 파드(Pod) 사이를 연결하기 위해 엔드포인트슬라이스 객체를 채움
        - 서비스어카운트 컨트롤러(ServiceAccount controller): 새로운 네임스페이스에 대해 기본 서비스어카운트(ServiceAccount)를 생성함

### cloud-controller-manager

- 클라우드별 제어 로직을 포함하는 쿠버네티스 컨트롤 플레인 컴포넌트임
- 클라우드 컨트롤러 매니저를 통해 클러스터를 클라우드 공급자의 API에 연결하고, 해당 클라우드 플랫폼과 상호 작용하는 컴포넌트와 클러스터 내부에서만 상호작용하는 컴포넌트를 분리할 수 있음
- 이 컴포넌트는 사용 중인 클라우드 제공업체와 관련된 컨트롤러만 실행함
    - 자체 온프레미스 환경이나 학습용 PC 환경에서 실행 중인 클러스터에는 클라우드 컨트롤러 매니저가 존재하지 않음
- kube-controller-manager와 마찬가지로, 클라우드 컨트롤러 매니저도 논리적으로 독립된 여러 제어 루프를 단일 프로세스로 실행되는 단일 바이너리로 결합함
- 성능 향상이나 장애 허용성(tolerance)을 높이기 위해 수평 확장이 가능함
- 다음과 같은 컨트롤러는 클라우드 공급자 의존성을 가질 수 있음:
    - 노드 컨트롤러(Node controller): 노드가 응답을 멈춘 뒤 클라우드에서 해당 노드가 삭제되었는지 판단하기 위해 클라우드 공급자를 확인함
    - 라우트 컨트롤러(Route controller): 클라우드 인프라에 네트워크 경로(Route)를 설정함
    - 서비스 컨트롤러(Service controller): 클라우드 공급자의 로드 밸런서를 생성, 업데이트, 삭제함

## Node components

- 노드 컴포넌트는 모든 노드에서 실행되며, 실행 중인 파드를 유지하고 쿠버네티스 런타임 환경을 제공함

### kubelet

- 클러스터의 각 노드에서 실행되는 에이전트
- kubelet은 파드에서 컨테이너가 확실하게 동작하도록 관리함
- kubelet은 다양한 메커니즘을 통해 제공된 파드 스펙(PodSpec)의 집합을 받아서 컨테이너들이 정상적으로 실행되고, 건강한 상태(healthy)인지 확인함
- kubelet은 쿠버네티스를 통해 생성되지 않는 컨테이너는 관리하지 않음

### Container runtime

- 컨테이너 런타임은 컨테이너 실행을 담당하는 소프트웨어임
- 쿠버네티스는 containerd, CRI-O와 같은 컨테이너 런타임 및 모든 Kubernetes CRI(Container Runtime Interface) 구현체를 지원함

## Addons

- 애드온은 쿠버네티스 리소스(DaemonSet, Deployment 등)를 사용하여, 클러스터의 기능을 구현함
- 클러스터 단위의 기능을 제공하기 때문에 애드온 관련 리소스는 `kube-system` 네임스페이스에 속함

### DNS

- 다른 애드온은 필수사항은 아니지만, 모든 클러스터에는 클러스터 DNS를 갖춰야 함
- 클러스터 DNS는 쿠버네티스 서비스에 대한 DNS 레코드를 제공하는 DNS 서버
    - 사용자 환경에 있는 다른 DNS 서버와 별개로 동작함
- 쿠버네티스에 의해 실행된 컨테이너는 자동으로 이 DNS 서버를 DNS 검색에 포함함

### 웹 UI (대시보드)

- 대시보드는 쿠버네티스 클러스터를 위한 범용 웹 기반 UI
- 사용자는 이를 통해 클러스터 자체 뿐만 아니라 클러스터에서 실행중인 애플리케이션을 관리하고 문제를 해결할 수 있음

### 컨테이너 리소스 모니터링

- 컨테이너에 대한 일반적인 시계열 메트릭을 중앙 데이터베이스에 기록하고, 해당 데이터를 탐색할 수 있는 UI를 제공함

### 클러스터 수준 로깅

- 클러스터 수준 로깅 메커니즘은 컨테이너 로그를 검색/탐색 인터페이스를 갖춘 중앙 로그 저장소에 저장하는 역할을 함

### 네트워크 플러그인

- 네트워크 플러그인 CNI(Cotainer Network Interface) 사양을 구현한 소프트웨어 컴포넌트임
    - 파드에 IP 주소를 할당하고 클러스터 내에서 서로 통신할 수 있게 함

## Architecture variations

- 쿠버네티스의 핵심 컴포넌트는 일관되지만, 배포 및 관리 방식은 다양할 수 있음
    - 이러한 변형을 이해하는 것은 특정 운영 요구 사항을 충족하는 쿠버네티스 클러스터를 설계하고 유지하는 데 매우 중요함
- 쿠버네티스 아키텍처의 유연성 덕분에 조직은 기능 복잡성, 성능, 관리 부담과 같은 요소들을 균형있게 고려하여 클러스터를 특정 요구사항에 맞게 조정할 수 있음

### 컨트롤 플레인 배포 옵션

- 컨트롤 플레인 컴포넌트는 여러 방식으로 배포될 수 있음

#### 기본적인 배포 (Traditional)

- 컨트롤 플레인 컴포넌트가 전용 머신이나 VM에서 직접적으로 실행되며, 보통 systemd 서비스로 관리됨

#### 정적 파드 (Static Pods)

- 컨트롤 플레인 컴포넌트가 정적 파드로 배포되며, 특정 노드의 kubelet에 의해 관리됨
    - 이는 kubeadm과 같은 도구에서 흔히 사용하는 방식임

#### 셀프 호스팅 (Self-hosted)

- 컨트롤 플레인이 쿠버네티스 클러스터 내부에서 파드로 실행됨 
    - 이 파드들은 디플로이먼트(Deployment)와 스테이트풀셋(StatefulSet) 같은 쿠버네티스 리소스에 의해 관리됨

#### 관리형 서비스 (Managed Kubernetes services)

- 클라우드 제공업체가 컨트롤 플레인을 추상화하여 서비스의 일부로 직접 관리함

### 워크로드 배치 고려사항

- 컨트롤 플레인 컴포넌트를 포함한 워크로드 배치는 클러스터의 크기, 성능 요구사항, 운영 정책에 따라 달라질 수 있음
    - 소규모나 개발용 클러스터에서는 컨트롤 플레인 컴포넌트와 사용자 워크로드가 동일한 노드에서 실행될 수 있음
    - 대규모 운영 환경에서는 보통 컨트롤 플레인 전용 노드를 두어 사용자 워크로드와 분리함
    - 일부 조직은 중요한 애드온이나 모니터링 도구를 컨트롤 플레인에서 실행함

### 클러스터 관리 도구

- `kubeadm`, `kops`, `Kubespray` 같은 도구들은 클러스터를 배포하고 관리하는데 서로 다른 접근 방식을 제공함
    - 각 도구는 고유한 컴포넌트 배치 및 관리 방식을 가짐

### 사용자 정의(커스터마이제이션) 및 확장성

- 쿠버네티스 아키텍처는 다양한 사용자 정의(커스터마이제이션)을 허용함
    - 기본 쿠버네티스 스케줄러와 함께 동작하거나 완전히 대체하기 위해 커스텀 스케줄러를 배포할 수 있음
    - CRD(CustomResourceDefinitions) 및 API Aggregation(API 집계)를 통해 API 서버를 확장할 수 있음
    - 클라우드 공급자는 cloud-controller-manager를 사용하여 쿠버네티스와 긴밀하게 통합할 수 있음
