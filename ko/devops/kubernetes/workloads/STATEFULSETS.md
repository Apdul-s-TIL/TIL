# StatefulSets

## StatefulSet(스테이트풀셋)이란?

- 스테이트풀셋은 파드 그룹을 실행하고, 각 파드에 대해 고정된 식별자(Sticky Identity)를 유지하는 워크로드 API 오브젝트임
- 영구 저장소(Persistent Storage)나 고유하고 안정적인 네트워크 식별자가 필요한 Stateful한 애플리케이션을 관리하는데 유용함
- 디플로이먼트와 유사하게, 스테이트풀셋은 동일한 컨테이너 스펙을 기반으로 둔 파드들을 관리함
  - 다만 디플로이먼트와 다르게, 스테이트풀셋은 각 파드의 독자성을 유지함
    - 이 파드들은 동일한 스펙으로 생성되었지만, 서로 교체는 불가능함
    - 각 파드는 재스케줄링 간에도 지속적으로 유지되는 고유한 식별자를 가짐
- 스토리지 볼륨을 사용해서 워크로드에 지속성을 제공하려는 경우, 솔루션의 일부로 스테이트풀셋을 사용할 수 있음
  - 스테이트풀셋의 개별 파드는 장애에 취약하지만, 퍼시스턴트 파드 식별자(고유 식별자) 덕분에 기존 볼륨을 대체 파드에 쉽게 다시 연결할 수 있음

## 스테이트풀셋 활용 사례

- 스테이트풀셋은 다음 항목 중 하나 이상이 필요한 애플리케이션에 적합함
  - 안정적이고 고유한 네트워크 식별자
  - 안정적이고 지속적인 스토리지
  - 순차적이고 정상 배포(graceful deployment) 및 스케일링
  - 순차적이고 자동화된 롤링 업데이트
- 위의 `안정적(stable)`이라는 표현은 파드가 재스케줄링되어도 유지됨을 의미함
  - 만약 식별자나 순차적 배포, 삭제 또는 스케일링이 필요 없는 애플리케이션이라면 디플로이먼트나 레플리카셋 같은 Stateless 워크로드를 사용하는 것이 더 적합함

## 제한사항(Limitations)

- 파드에 지정된 스토리지는 스토리지 클래스(StorageClass)을 기반으로 하는 퍼시스턴트 볼륨 프로비지너가 동적 생성하거나 관리자가 사전에 만들어 두어야 함
- 스테이트풀셋을 삭제 또는 스케일 다운하더라도 스테이트풀셋과 연결된 볼륨(PVC/PV)은 삭제되지 않음
  - 이는 데이터 안전을 보장하기 위함
- 스테이트풀셋은 현재 파드의 네트워크 식별자를 담당할 헤드리스 서비스(Headless Service)가 필수적이며, 사용자가 직접 생성해야 함
- 스테이트풀셋 삭제 시 파드의 종료에 대한 어떠한 보증을 제공하지 않음
  - 스테이트풀셋에서는 파드가 순차적이고 정상적으로 종료(graceful termination)되도록 하려면, 삭제 전 스테이트풀셋의 스케일을 0으로 먼저 축소하는 것이 좋음
- 기본 파드 관리 정책(`OrderedReady`)을 사용하는 롤링 업데이트 중 장애가 발생하면 수동 개입이 필요한 상태에 빠질 수 있음

## 구성 요소(Components)

### 예시

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx
  labels:
    app: nginx
spec:
  ports:
  - port: 80
    name: web
  clusterIP: None
  selector:
    app: nginx
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  selector:
    matchLabels:
      app: nginx # .spec.template.metadata.labels 와 일치해야 한다
  serviceName: "nginx"
  replicas: 3 # 기본값은 1
  minReadySeconds: 10 # 기본값은 0
  template:
    metadata:
      labels:
        app: nginx # .spec.selector.matchLabels 와 일치해야 한다
    spec:
      terminationGracePeriodSeconds: 10
      containers:
      - name: nginx
        image: registry.k8s.io/nginx-slim:0.8
        ports:
        - containerPort: 80
          name: web
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes: [ "ReadWriteOnce" ]
      storageClassName: "my-storage-class"
      resources:
        requests:
          storage: 1Gi
```

### 파드 셀렉터

- 스테이트풀셋의 `.spec.selector` 필드는 `.spec.template.metadata.labels` 레이블과 일치하도록 설정해야 함
- 해당되는 파드 셀렉터를 찾지 못하면 스테이트풀셋 생성 과정에서 검증 오류가 발생함

### 볼륨 클레임 템플릿

- `.spec.volumeClaimTemplates` 필드를 설정하여 PersistentVolumeClaim을 생성할 수 있음
- 다음 두 조건 중 하나를 만족하면 스테이트풀셋에 안정적인 스토리지를 제공함
  - 볼륨 클레임에 지정된 스토리지클래스가 동적 프로비저닝을 사용하도록 설정되어 있음
  - 클러스터에 올바른 스토리지클래스와 충분한 저장 공간을 가진 PersistentVolume이 이미 존재하는 경우

### 최소 준비 시간 초

- `.spec.minReadySeconds`는 파드가 사용 가능(available)이라고 간주될 수 있도록 파드의 모든 컨테이너가 문제 없이 실행되고 준비되는 최소 시간(초)을 나타내는 선택적인 필드임
- 롤링 업데이트 전략을 사용할 때, 롤아웃 진행 상황을 확인하는데 사용됨 
- 이 필드의 기본값은 0임
  - 이 경우, 파드가 Ready 상태가 되면 바로 사용 가능하다고 간주됨

## 파드 식별자(Pod Identity)

- 스테이트풀셋의 파드는 순서, 안정적인 네트워크 ID, 안정적인 스토리지로 구성된 고유 식별자를 가짐
- 식별자는 파드가 어떤 노드에 있는지나 (재)스케줄과도 상관없이 파드에 붙어있음

### 순서 색인(Ordinal Index)

- N개의 레플리카가 있는 스테이트풀셋의 경우 각 파드에는 `0`부터 `N-1`까지의 정수가 순서대로 할당되며, 해당 스테이트풀셋 내에서 고유함
- 또한 스테이트풀셋 컨트롤러는 `apps.kubernetes.io/pod-index`과 같은 인덱스 값을 가진 파드 레이블을 추가함 

### 시작 순서

- `.spec.ordinals`은 각 파드에 할당할 순서에 대한 정수값을 설정할 수 있게 해주는 선택적인 필드
  - 기본값은 nil임
  - 만약 `.spec.ordinals.start` 필드를 설정하면, 파드는 `.spec.ordinals.start`부터 `.spec.ordinals.start + .spec.replicas - 1`의 순서대로 할당됨

### 안정적인 네트워크 ID

- 스테이트풀셋의 각 파드는 스테이트풀셋의 이름과 파드의 순번에서 호스트네임을 얻음
  - 호스트네임을 구성하는 패턴은 `$(statefulset name)-$(ordinal)`임
- 스테이트풀셋은 스테이트풀셋에 있는 파드의 도메인을 제어하기 위해 헤드리스 서비스를 사용할 수 있음
  - 이 서비스가 관리하는 FQDN(전체 도메인 이름)은 다음과 같은 형식을 가짐
    - `$(service name).$(namespace).svc.cluster.local`
    - 여기서 `cluster.local`은 클러스터 도메인임
  - 각 파드가 생성되면 다음과 같은 형식과 일치하는 DNS 서브도메인을 가지며, 여기서 거버닝 서비스(governing service)는 스테이트풀셋의 `serviceName` 필드에 의해 정의됨
    - `$(podname).$(governing service domain)`
    - 파드 전체 DNS 주소: `$(pod name).$(service name).$(namespace).svc.cluster.local`
- DNS 캐싱 참고
  - 클러스터에서 DNS가 구성된 방식에 따라, 새로 실행된 파드의 DNS 이름을 즉시 찾지 못할 수 있음
    - 이 동작은 클러스터의 다른 클라이언트가 파드가 생성되기 전에 파드의 호스트 이름에 대한 쿼리를 이미 보낸 경우에 발생할 수 있음
    - 네거티브 캐싱(DNS에서 일반적)은 이전에 실패한 조회 결과가 파드가 실행된 후에도 적어도 몇 초 동안 기억되고 재사용됨을 의미함
  - 파드를 생성한 후 즉시 파드를 검색해야 하는 경우, 몇 가지 옵션이 있음
    - DNS 조회에 의존하지 않고, 쿠버네티스 API를 직접 쿼리하기
    - 쿠버네티스 DNS 공급자의 캐싱 시간(일반적으로 CoreDNS의 ConfigMap을 편집하는 것을 의미하며, 현재 30초 동안 캐시함)을 줄이기

### 안정직인 스토리지(Stable Storage)

- `.spec.volumeClaimTemplates`에 정의된 각 항목에 대해 각 파드는 하나의 PersistentVolumeClaim(PVC)을 생성 받음
  - 만약 스토리지 클래스가 명시되지 않은 경우, 기본 스토리지 클래스가 사용됨
- 파드가 노드에서 스케줄 혹은 재스케줄이 되면 파드의 `volumeMounts`는 기존 PVC와 연결된 PV가 마운트 됨
  - 참고로 파드의 PVC와 관련된 PV는 파드 또는 스테이트풀셋이 삭제되더라도 삭제되지 않음
  - 이것은 반드시 수동으로 삭제해야 함

### 파드 이름 레이블

- 스테이트풀셋 컨트롤러가 파드를 생성할 때 파드 이름으로 `statefulset.kubernetes.io/pod-name` 레이블이 추가됨
  - 이 레이블로 스테이트풀셋의 특정 파드에 서비스를 연결할 수 있음

### 파드 인덱스 레이블

- 스테이트풀셋 컨트롤러가 파드를 만들 때, 새로운 파드는 `apps.kubernetes.io/pod-index`로 레이블링 됨
  - 이 레이블의 값은 파드의 인덱스 순서임
  - 이 레이블을 사용하면 다음과 같은 작업을 수행할 수 있음
    - 특정 파드 인덱스로 트래픽을 라우팅하기 
    - 파드 인덱스 레이블을 사용하여 로그/메트릭을 필터링

## 배포 및 스케일링 보장(Deployment and Scaling Guarantees)

- N개의 복제본을 가진 스테이트풀셋은 다음과 같은 엄격한 순서를 따름
  1. 순차 생성: 파드는 `{0..N-1}` 순서대로 하나씩 생성됨
  2. 역순 삭제: 파드가 삭제될 때는 `{N-1..0}` 역순으로 종료됨
  3. 선행 파드 준비 완료 필수: 다음 파드를 생성/스케일링하기 전, 이전 파드가 반드시 `Running` 및 `Ready` 상태여야 함
  4. 후속 파드 종료 완료 필수: 특정 파드를 종료하기 전, 뒤 순번의 파드가 완전히 종료되어야 함
- 스테이트풀셋은 `pod.Spec.TerminationGracePeriodSeconds`을 0으로 명시하면 안 됨

### 파드 관리 정책(Pod Management Policies)

- 스테이트풀셋의 `.spec.podManagementPolicy` 필드를 통해 고유성 및 신원 보증을 유지하면서 순서 봐장 제약을 완화함
- `OrderReady` 파드 관리(기본값)
  - 앞서 설명한 엄격한 순차 배포/종료 규칙을 따름
- `Parallel` 파드 관리
  - 스테이트풀셋 컨트롤러에게 모든 파드를 병렬로 실행 또는 종료하게 함
  - 다른 파드의 실행이나 종료에 앞서 파드가 Running 및 Ready 상태가 되거나, 완전히 종료되기를 기다리지 않음
  - 이 옵션은 오직 스케일링 작업에 대한 동작에만 영향을 미침
    - 업데이트는 영향을 받지 않음

## 업데이트 전략(Update Strategies)

- `.spec.updateStrategy.type` 필드를 통해 업데이트 방식을 지정함
- `RollingUpdate`(기본값)
  - 스테이트풀셋의 각 파드를 하나씩 삭제하고 재생성함
  - 파드 종료 순서와 동일하게 `{N-1..0}` 순서대로 진행됨
  - 파티션 롤링 업데이트(`.spec.updateStrategy.rollingUpdate.partition`)
    - 파티션 값을 지정하면 해당 값 이상의 순서를 가진 파드만 업데이트 됨
    - 파티션보다 작은 순서의 파드는 템플릿이 바뀌어도 이전 버전을 유지함
    - 카나리 배포나 단계별 롤아웃 시 유용함
  - 최대 불가 파드 수(`maxUnavailable`)
    - 업데이트 중 동시에 사용할 수 없는 최대 파드 수를 설정함
    - 기본값은 1임
  - 문제 상황 시 강제 롤백(Forced Rollback)
    - 잘못된 설정으로 인해 업데이트 중인 파드가 `Ready` 상태에 도달하지 못하면 롤아웃이 멈춤
    - 이 때 템플릿을 정상 설정으로 돌리는 것만으로는 부족하며, 잘못된 설정으로 생성되어 멈춰있는 파드를 직접 삭제해주어야 정상 템플릿으로 다시 생성되기 시작함
- `OnDelete`
  - 자동 업데이트를 수행하지 않음
  - 사용자가 직접 파드를 삭제해야만 새로운 템플릿 기반의 새로운 파드가 생성됨
- `Recreate`
  - 모든 파드를 한 번에 먼저 삭제한 뒤, 완전히 종료되면 새 파드들을 생성함
  - 이전 버전과 새 버전이 동시에 실행될 수 없는 애플리케이션(공유 리소스 독점 필요 등)에 유용하지만 다운타임이 발생함

## 수정 내역

- 스테이트풀셋은 설정 변경 이력을 추적하고 롤백하기 위해 ControllerRevision 오브젝트를 사용함
- 스테이트풀셋이 ControllerRevision을 사용하여 변경 사항을 추적하는 방법
  - 스테이트풀셋의 파드 템플릿(`spec.template`)을 업데이트하면 스테이트풀셋 컨트롤러는 다음을 수행함
    - 새 ControllerRevision 오브젝트를 준비함
    - 파드 템플릿 및 메타 데이터의 스냅샷을 저장함
    - 증분 수정 번호를 할당함

### 수정 내역 관리

- `.spec.revisionHistoryLimit`을 사용하여 보관된 수정 내역을 제어함
- 지정하지 않으면 수정 내역 10개(기본값)가 유지됨
  - 0으로 설정 시 롤백 기능이 비활성화됨
- 제한을 초과하면 가장 오래된 수정 내역이 가비지 컬렉션됨

### Best Practices

- 보존 정책
  - 대부분의 워크로드에 대해 `revisionHistoryLimit`을 5~10 사이로 설정함
  - 심층 롤백 기록이 필요한 경우에만 늘림
- 모니터링
  - 다음을 사용하여 정기적으로 개정 내용을 확인함
    ```
    kubectl get controllerrevisions
    ```
  - 급격한 개정 횟수 증가 알림
- 피해야 할 사항
  - ControllerRevision 오브젝트를 수동으로 편집하지 않아야 함
  - 리비전을 백업 메커니즘으로 사용하지 않아야 함
    - 실제 백업 도구를 사용해야 함
  - `revisionHistoryLimit: 0`으로 설정
    - 롤백 기능을 비활성화함

## PVC 보존 정책(PersistentVolumeClaim Retention)

- 선택적 필드인 `.spec.persistentVolumeClaimRetentionPolicy`를 통해 스테이트풀셋의 생명주기 동안 PVC를 자동으로 삭제할지 여부를 제어할 수 있음
- 이 필드를 사용하려면 API 서버와 컨트롤러 매니저에 `StatefulSetAutoDeletePVC` 기능 게이트를 활성화해야 함
- 활성화 시, 각 스테이트풀셋에 대해 다음 두 가지 정책을 설정할 수 있음
  - `whenDeleted`
    - 스테이트풀셋이 삭제될 때 적용될 볼륨 유보 동작을 설정함
  - `whenScaled`
    - 스테이트풀셋의 레플리카 수가 줄어들 때(e.g. 스테이트풀셋을 스케일 다운할 때), 적용될 볼륨 유보 동작을 설정함
- 설정 가능한 각 정책에 대해, 그 값을 `Delete` 또는 `Retain`으로 설정할 수 있음
  - `Retain`(기본값)
    - 파드가 삭제되어도 `volumeTemplate`으로부터 생성된 PVC는 영향을 받지 않음
  - `Delete`
    - 정책 조건(삭제 또는 축소)에 해당하는 파드가 제거될 때, 해당 PVC도 함께 삭제됨
- 이러한 정책은 파드의 삭제가 스테이트풀셋 삭제 또는 스케일 다운으로 인한 것일 때에만 적용됨에 유의해야 함
  - 예를 들어 스테이트풀셋의 파드가 노드 실패로 인해 실패했고, 컨트롤 플레인이 대체 파드를 생성했다면, 스테이트풀셋은 기존 PVC를 유지함
    - 기존 볼륨은 영향을 받지 않으며, 새 파드가 실행될 노드에 클러스터가 볼륨을 연결(attach)함
- 스테이트풀셋 컨트롤러는 자신이 소유한 PVC에 소유자 정보(reference)를 추가하여, 파드가 종료된 후에는 가비지 콜렉터가 이 정보를 삭제함
  - 이로 인해 PVC가 삭제되기 전에(그리고 유보 정책에 따라 매칭되는 기반 PV와 볼륨이 삭제되기 전에) 파드가 모든 볼륨을 깨끗하게 언마운트할 수 있음
  - `whenDeleted` 정책을 `Delete`로 설정하면, 해당 스테이트풀셋에 연결된 모든 PVC에 스테이트풀셋 인스턴스의 소유자 정보가 기록됨
- `whenScaled` 정책은 파드가 스케일 다운되었을 때에만 PVC를 삭제하며, 파드가 다른 원인으로 삭제되면 PVC를 삭제하지 않음
  - 조정 상황 발생 시, 스테이트풀셋 컨트롤러는 목표 레플리카 수와 클러스터 상의 실제 파드 수를 비교함
  - 레플리카 카운트보다 큰 ID를 갖는 스테이트풀셋 파드는 부적격 판저을 받으며 삭제 대상으로 표시됨
  - `whenScaled` 정책이 `Delete`이면, 부적격 파드는 삭제되기 전에 연결된 스테이트풀셋 템플릿 PVC의 소유자로 지정됨
  - 이로 인해 부적격 파드가 종료된 이후에만 PVC가 가비지 콜렉트됨
- 만약 컨트롤러가 강제 종료되어 재시작되면, 파드의 소유자 정보가 정책에 적합하게 업데이트되기 전에는 어떤 파드도 삭제되지 않을 것임을 의미함
  - 만약 컨틀롤러가 다운된 동안 부적격 파드가 강제로 삭제되면, 컨트롤러가 강제 종료된 시점에 따라 소유자 정보가 설정되었을 수도 있고 설정되지 않았을 수도 있음
  - 소유자 정보가 업데이트되기까지 몇 번의 조정 절차가 필요할 수 있음
  - 따라서 일부 부적격 파드는 소유자 정보 설정을 완료하고 나머지는 그러지 못했을 수 있음
  - 이러한 이유로 컨트롤러가 다시 켜져서 파드를 종료하기 전에 소유자 정보를 검증할 때까지 기다리는 것을 추천함
    - 이것이 불가능하다면, 관리자는 PVC의 소유자 정보를 확인하여 파드가 강제 삭제되었을 때 해당되는 오브젝트가 삭제되도록 해야 함

### 레플리카

- `.spec.replicas`은 필요한 파드의 수를 지정하는 선택적 필드임
  - 기본값은 1임
- `HorizontalPodAutoscaler(HPA)`가 디플로이먼트 크기를 관리하고 있다면, `.spec.replicas`를 설정해서는 안 됨
  - 대신 쿠버네티스 컨트롤 플레인이 `.spec.replicas` 필드를 자동으로 관리함
