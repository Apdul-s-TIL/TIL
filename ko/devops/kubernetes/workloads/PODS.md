# Pods

## Pod(파드)란?

- 파드는 쿠버네티스에서 생성하고 관리할 수 있는 배포 가능한 가장 작은 컴퓨팅 단위임
- 파드(고래 떼나 꼬투리라는 뜻의 단어)는 하나 이상의 컨테이너 그룹임
    - 이 그룹은 공동의 스토리지 및 네트워크를 공유하고, 해당 컨테이너를 구동하는 방식에 대한 명세도 공유함
- 파드의 구성 요소들은 항상 함께 배치(Co-located)되고, 함께 스케줄링(Co-scheduled)되며, 공유 컨텍스트(Context)에서 실행됨
- 파드는 애플리케이션 고유의 '논리적 호스트(Logical Host)' 역할을 하며, 비교적 밀접하게 결합된 하나 이상의 애플리케이션 컨테이너를 포함함
- 파드에는 애플리케이션 컨테이너뿐만 아니라, 파드가 시작될 때 실행되는 초기화 컨테이너(Init containers)를 포함할 수 있으며, 실행 중인 파드를 디버깅하기 위해 임시 컨테이너(Ephemeral containers)를 주입할 수도 있음

### 참고 사항

- 파드가 노드에서 실행되려면 클러스터의 각 노드에 컨테이너 런타임이 설치되어 있어야 함
- 파드가 공유하는 컨텍스트는 리눅스 네임스페이스(Linux Namespaces), cgroups 및 기타 격리 요소의 집합으로, 일반 컨테이너를 격리하는 메커니즘과 동일함
    - 파드 컨텍스트 안에서 개별 애플리케이션은 추가적인 하위 격리를 적용받을 수도 있음
- 파드는 네임스페이스와 파일 시스템 볼륨을 공유하는 컨테이너들의 집합과 유사함

## Pod의 사용 방식

> 쿠버네티스 클러스터에서 파드는 크게 다음과 같은 두 가지 방식으로 사용됨

- 단일 컨테이너를 실행하는 파드
    - "파드 당 1개의 컨테이너(one-container-per-pod)" 모델은 가장 일반적인 쿠버네티스 유스케이스임
    - 이 경우 파드는 단일 컨테이너를 감싸는 래퍼(wrapper)처럼 볼 수 있으며, 쿠버네티스는 컨테이너 자체가 아니라 파드를 관리함
- 함께 동작해야 하는 여러 컨테이너를 실행하는 파드
    - 파드는 서로 긴밀하게 결합되어 리소스를 공유해야 하는 여러 개의 컨테이너로 구성된 애플리케이션을 캡슐화할 수 있음
    - 이 컨테이너들은 하나의 응집력 있는 단위를 이룸

### 파드 사용 시 주의사항

- 여러 개의 컨테이너를 하나의 파드 안에 두고 관리하여 그룹화하는 것은 상대적으로 고급 사용 사례임
- 컨테이너들이 긴밀히 결합되어 있는 특정한 상황에서만 이 패턴을 사용하는 것을 권장함
- 고가용성이나 용량 확장을 위해 여러 복제본(Replica)를 둘 목적이라면 파드 안에 여러 컨테이너를 넣지 말고, 워크로드 관리 기능을 사용해야 함

### 파드를 관리하기 위한 워크로드 리소스

- 일반적으로 단일 파드(Singleton Pod)라 할지라도 파드를 직접 생성할 필요가 없음
    - 대신 Deployment나 Job과 같은 워크로드 리소스를 사용하여 생성함
    - 만약 파드가 상태를 유지해야(Track state) 한다면 StatefulSet 리소스 사용을 고려해야 함
- 각 파드는 특정 애플리케이션의 단일 인스턴스를 실행하도록 설계됨
    - 애플리케이션을 수평으로 확장(더 많은 인스턴스를 실행하여 전체 리소스 확보)하려면 각 인스턴스에 하니씩 여러 개의 파드를 사용해야 함
        - 쿠버네티스에서는 이를 일반적으로 레플리케이션(Replication)dlfk gka
        - 복제된 파드는 보통 워크로드 리소스와 그 컨트롤러에 의해 그룹으로 생성되고 관리됨
- 파드는 기본적으로 파드에 속한 구성 컨테이너들에게 네트워크와 스토리지라는 두 가지 종류의 공유 리소스를 제공함

## 파드 작업

- 쿠버네티스에서 개별 파드를 직접 생성하는 경우는 거의 없음
    - 파드가 비교적 일시적이고 언제든 교체 가능한(Ephemeral, disposable) 엔티티로 설계되었기 때문임
- 파드가 생성될 때(사용자가 직접 또는 컨트롤러가 간접적으로), 새 파드가 생성되면 클러스터 내의 특정 노드에서 실행되도록 스케줄링 됨
- 파드는 다음과 같은 상황이 발생하기 전까지 해당 노드에 계속 남아있게 됨
    - 파드의 실행이 성공적으로 완료됨
    - 파드 오브젝트가 삭제됨
    - 리소스 부족으로 인해 파드가 축출(Eviction) 됨
    - 파드가 실행 중이던 노드가 고장(Fail)남

### 파드 작업 시 참고 사항

- 파드 내의 컨테이너를 재시작하는 것과 파드 자체를 재시작하는 것을 혼동해서는 안 됨
    - 파드는 프로세스가 아니라 컨테이너가 실행되는 '환경'임
    - 파드는 명시적으로 삭제될 때까지 소멸하지 않고 유지됨
- 파드의 이름은 유효한 DNS 서브도메인 값이어야 하지만, 이는 파드 호스트네임에 예상치 못한 결과를 초래할 수 있음
    - 호환성을 극대화하려면 좀 더 엄격한 규칙인 DNS 레이블(DNS Label) 규칙을 따르는 이름이 좋음

### 파드 OS

- 파드가 실행될 OS를 지정하려면, `.spec.os.name` 필드를 `windows` 또는 `linux`로 설정해야 함
    - 현재 쿠버네티스(Kubernetes v1.25)에서 지원하는 운영체제는 이 두 가지뿐이며, 향후 확장될 수 있음
- 쿠버네티스 v1.36 기준으로 `.spec.os.name` 값은 `kube-scheduler`가 파드를 실행할 노드를 선택하는 방식에 직접적인 영향을 주지 않음
    - 다양한 OS 노드가 섞여 있는 클러스터라면, 각 노드에 `kubernetes.io/os` 레이블을 올바르게 설정하고, 파드 사양에 이 레이블을 기반으로 한 `nodeSelector`를 정의해야 함
- 파드 시큐리티 스탠다드(Pod Security Standards) 기능도 이 필드를 활용해 해당 OS와 관련 없는 정책이 강제 적용되지 않도록 함

### 파드와 컨트롤러(Pods and controllers)

- 워크로드 리소스를 사용하면 여러 개의 파드를 자동으로 생성하고 관리할 수 있음
- 리소스에 대한 컨트롤러는 복제(Replication), 롤아웃(Rollout) 및 실패 시의 자동 복구(Auto-healing)를 처리함
    - 예를 들어 노드가 고장 나면, 컨트롤러는 해당 노드의 파드가 작동을 멈춘 것을 감지하고 대체 파드를 생성하며, 스케줄러는 이 대체 파드를 건강한 다른 노드에 배치함
- 하나 이상의 파드를 관리하는 대표적인 워크로드 리소스 예시는 다음과 같음
    - Deployment
    - StatefulSet
    - DaemonSet

### 스케줄링 그룹 지정(Specifying a scheduling group)

- 기본적으로 쿠버네티스는 모든 파드를 개별적으로 스케줄링 함
    - 그러나 밀접하게 결합된 일부 애플리케이션은 정상 작동을 위해 여러 파드 그룹이 동시에 스케줄링되어야 함
- 사용자는 스케줄링 그룹 필드(`.spec.schedulingGroup`)를 사용해 파드를 특정 `PodGroup`에 연결할 수 있음
    - 이를 통해 `kube-scheduler`에게 이 파드가 특정 그룹에 속해 있음을 알리고, 전체 그룹에 대해 한 번에 조율된 배치 결정을 내리도록 할 수 있음
- 해당 기능은 Kubernetes v1.35[Alpha] 부터 사용 가능하며, 기본적으로 비활성화됨

### 파드 템플릿

- 워크로드 리소스의 컨트롤러는 파드 템플릿(PodTemplate)을 바탕으로 사용자를 대신해 실제 파드를 생성하고 관리함
- PodTemplate는 파드 생성을 위한 명세서(Specification)로, Deployments, Jobs, DaemonSets 같은 워크로드 리소스 내부에 포함되어 있음
- 워크로드 컨트롤러는 오브젝트 내부의 파드 템플릿을 사용해 실제 파드를 찍어내며, 이 템플릿은 애플리케이션이 유지해야 할 '원하는 상태(Desired state)'의 일부가 됨
- 파드 템플릿을 수정하거나 새로운 템플릿으로 교체하더라도 이미 기존에 실행 중인 파드에 직접적인 영향을 주지는 않음
    - 워크로드 리소스의 파드 템플릿을 변경하면, 해당 리소스는 업데이트된 템플릿을 사용하는 대체 파드를 새로 생성해야 함
    - 예를 들어, StatefulSet 컨트롤러는 실행 중인 파드가 각 StatefulSet 오브젝트의 현재 파드 템플릿과 일치하도록 보장함
        - StatefulSet을 편집하여 파드 템플릿을 변경하면, StatefulSet은 업데이트된 템플릿을 기반으로 새 파드를 생성하기 시작함
        - 결과적으로 모든 기존 파드가 새 파드로 교체되면서 업데이트가 완료됨
- 노드 레벨에서 작동하는 `kubelet`은 파드 템플릿이나 업데이트에 관한 세부 사항을 직접 관찰하거나 관리하지 않으며, 이러한 상세 내용은 추상화되어 가려짐
    - 이와 같은 관심사 분리(Seperation of concerns) 덕분에 시스템 의미론이 단순해지고, 기존 코드를 수정하지 않고도 클러스터의 동작을 원활하게 확장할 수 있음 

## 파드 업데이트 및 교체(Pod update and replacement)

- 이전 섹션에서 언급한 바와 같이, 워크로드 리소스의 파드 템플릿이 변경되면 컨트롤러는 기존 파드를 그대로 수정(Update)하거나 패치(Patch)하는 대신, 업데이트된 템플릿을 기반으로 새로운 파드를 생성함
- 쿠버네티스가 사용자의 직접적인 파드 관리를 막지는 않으므로, 실행 중인 파드의 일부 필드를 제자리에서(In place) 업데이트하는 것은 가능함
    - 하지만 `patch`나 `replace` 같은 파드 업데이트 작업에는 몇 가지 제한 사항이 있음
        - 파드의 메타데이터(Metadata) 대부분은 변경 불가능(Immutable)함
            - 예를 들어 `namespace`, `name`, `uid`, `creationTimestamp` 필드는 변경할 수 없음
        - `metadata.deletionTimestamp`가 설정된 상태라면, `metadata.finalizers` 목록에 새로운 엔트리를 추가할 수 없음
        - 파드 업데이트 시 다음 필드 외에는 변경할 수 없음
            - `spec.containers[*].image`
            - `spec.initContainers[*].image`
            - `spec.activeDeadlineSeconds`
            - `spec.terminationGracePeriodSeconds`
            - `spec.tolerations`(단, 새 항목 추가만 가능)
            - `spec.scheduleGates`
        - `spec.activeDeadlineSeconds` 필드를 업데이트할 때는 다음 두 가지 유형만 허용됨
            - 할당되지 않은 필드에 양수 설정
            - 기존 양수에서 더 작은 비음수(0 또는 양수)로 업데이트

### 파드 서브리소스(Pod subresources)

- 앞서 설명한 업데이트 규칙은 일반적인 파드 업데이트에 적용되지만, 일부 필드는 서브리소스(Subresources)를 통해 업데이트 할 수 있음
    - 리사이즈(Resize)
        - `resize` 서브리소스를 사용하면 컨테이너 리소스 사양(`spec.containers[*].resources`)을 업데이트할 수 있음
    - 임시 컨테이너(Ephemeral Containers)
        - `ephemeralContainers` 서브리소스를 사용하면 실행 중인 파드에 임시 컨테이너를 추가할 수 있음
    - 상태(Status)
        - `status` 서브리소스를 사용하면 파드의 상태를 업데이트할 수 있음
        - 보통 `kubelet`과 시스템 컨트롤러들만 사용함
    - 바인딩(Binding)
        - `binding` 서브리소스를 사용하면 `Binding` 요청을 통해 파드의 `spec.nodeName`을 설정할 수 있으며, 주로 스케줄러가 사용함

### 파드 세대(Pod generation)

- `metadata.generation` 필드는 고유함
    - 시스템에 의해 자동 설정되어 새 파드의 `metadata.generation` 값은 기본적으로 `1`이 됨
    - 파드 `spec` 내의 변경 가능한 필드가 업데이트될 때마다 `metadata.generation` 값이 1씩 증가함
- `observedGeneration`은 파드 오브젝트의 `status` 섹션에 캡처되는 필드임
    - `kubelet`은 현재 파드 상태에 맞춰 파드 상태를 추적하기 위해 `status.observedGeneration`을 설정함
    - 이 필드는 파드 상태가 보고되는 시점의 `metadata.generation`을 반영함
    - 쿠버네티스 v1.35부터 가능하며, 기본적으로 활성화 됨
- 직접적인 상태 업데이트(Direct Status Updates)
    - 할당된 스펙이 직접적으로 바영되는 상태 필드인 경우, `observedGeneration`은 현재 `metadata.generation`(Generation N)과 연결됨
    - 이 동작은 다음과 같은 경우에 적용함
        - 리사이즈 상태(Resize Status): 리소스 리사이즈 작업의 상태임
        - 할당된 리소스(Allocated Resources): 리사이즈 이후 파드에 할당된 리소스임
        - 임시 컨테이너(Ephemeral Containers): 새 임시 컨테이너가 추가되어 `Waiting` 상태일 때
- 간접적인 상태 업데이트(Indirect Status Updates)
    - 실행 중인 스펙의 결과로 간접적으로 반영되는 상태 필드의 경우, `observedGeneration`은 이전 동기화 루프의 `metadata.generation`(Generation N-1)과 연결됨
    - 이 동작은 다음과 같은 경우에 적용함
        - 컨테이너 이미지: `ContainerStatus.ImageID`는 새 이미지가 풀(pull)되고 컨테이너가 업데이트되기 전까지 이전 세대의 이미지를 반영함
        - 실제 리소스: 리사이즈가 진행 중일 때, 실제 사용 중인 리소스는 이전 세대의 요처에 해당함
        - 컨테이너 상태: 리사이즈가 진행 중이고 재시작 정책이 필요할 경우, 이전 세대의 요청을 반영함
        - activeDeadlineSeconds & terminationGracePeriodSeconds & deletionTimestamp: 이 필드들이 파드 상태에 미치는 효과는 이전에 관찰된 스펙의 결과임

## 리소스 공유 및 통신(Resource sharing and communication)

### 파드 스토리지(Storage in Pods)

- 파드는 공유 스토리지 볼륨(Shared storage volume)의 집합을 지정할 수 있음
- 파드 내부의 모든 컨테이너는 이 공유 볼륨에 액세스할 수 있어 데이터를 공유할 수 있음
- 볼륨을 사용하면 내부 컨테이너 중 하나가 재시작되더라도 영구 데이터(Persistent data)가 삭제되지 않고 유지됨

### 파드 네트워킹(Pod networking)

- 각 파드에는 각 주소 패밀리(Address family) 별로 고유한 IP 주소가 할당됨
- 파드 내부의 모든 컨테이너는 IP 주소와 네트워크 포트를 포함한 네트워크 네임스페이스를 공유함
    - 따라서 파드 내부의 컨테이너들은 `localhost`를 사용하여 서로 통신할 수 있음
    - 반면, 파드의 컨테이너가 파드 외부의 엔티티와 통신할 때는 공유 네트워크 리소스(포트와 같은)를 어떻게 사용할지 서로 조율해야 함
    - 또한 파드 내 컨테이너들은 SystemV 세마포어나 POSIX 공유 메모리와 같은 표준 프로세스 간 통신(IPC)을 사용해 서로 통신할 수도 있음
        - 반면 서로 다른 파드에 속한 컨테이너들은 각자 고유한 IP 주소를 가지며, 특별한 설정 없이는 OS 레벨의 IPC로 통신할 수 없고 IP 네트워크를 통해 통신해야 함
- 파드 내부의 컨테이너가 바라보는 시스템의 호스트네임(Hostname)은 파드에 설정된 `name`과 동일하게 보임

## 파드 보안 설정(Pod security settings)

- 파드와 컨테이너에 보안 제약 조건을 설정하려면 파드 명세(Specification)의 `securityContext` 필드를 사용함
    - 이 필드를 통해 파드나 개별 컨테이너가 할 수 있는 다음과 같은 작업을 세밀하게 제어할 수 있음
        - 특정 리눅스 capabilities를 제거하여 CVE의 영향을 피함
        - 파드의 모든 프로세스를 루트가 아닌 사용자 또는 특정 사용자나 그룹 ID로 실행하도록 강제함
        - 특정 seccomp 프로파일을 설정함
        - 윈도우 보안 옵션을 설정함
- 기본적인 보안 구성을 위해서는 기본 파드 보안 표준(Baseline Pod security standard)을 충족하고 컨테이너를 non-root 사용자로 실행해야 함

## 리소스 요청 및 제한(Resource requests and limits)

- 파드를 지정할 때, 각 컨테이너가 필요한 리소스의 양을 선택적으로 명시할 수 있음
    - 가장 자주 지정하는 리소스는 CPU와 메모리(RAM)임
- 리소스 요청(Resource Request)
    - 컨테이너가 필요로 하는 최소한의 리소스 양
    - `kube-scheduler`는 이 정보를 바탕으로 파드를 어떤 노드에 배치할지 결정함
- 리소스 제한(Resource Limit)
    - 컨테이너가 사용할 수 있는 최대 리소스 한도
    - `kubelet`은 실행 중인 컨테이너가 설정된 제한을 초과하여 리소스를 사용하지 못하도록 강제함
- CPU와 메모리 제한 방식의 차이
    - CPU 제한
        - CPU 스로틀링(Throttling)을 통해 제어됨
        - 컨테이너가 한도에 도달하면 커널이 CPU 접근을 제한함
        - CPU 제한은 특정 워크로드가 동일 노드의 다른 워크로드를 굶기는 'Noisy neighbor' 문제를 방지하지만, 노드에 여유 CPU가 있어도 스로틀링이 발생해 지연에 민감한 워크로드의 성능을 떨어뜨릴 수 있는 트레이드오프가 존재함
    - 메모리 제한
        - 커널의 OOM(Out-Of-Memory) 킬러에 의해 강제됨
        - 컨테이너가 메모리 제한을 초과하면 프로세스가 강제 종료됨

## 정적 파드(Static Pods)

- 정적 파드는 API 서버의 관찰 없이 특정 노드의 `kubelet` 데몬이 직접 관리하는 파드임
- 대부분의 파드가 컨트롤 플레인(예를 들어, Deployment)에 의해 관리되는 것과 달리, 정적 파드는 `kubelet`이 각 정적 파드를 직접 감독하고 실패 시 재시작함
- 정적 파드는 항상 특정 노드의 `kubelet` 하나에 바인딩 됨
- 정적 파드의 주요 용도는 자가 호스팅 컨트롤 플레인(Self-hosted control plane)을 실행하는 것임
    - 즉, `kubelet`을 사용하여 개별 쿠버네티스 컨트롤 플레인 컴포넌트들을 감독하도록 할 때 주로 쓰임

## 다중 컨테이너를 가진 파드(Pods with multiple containers)

- 파드는 하나의 결속된 서비스 단위를 형성하는 여러 협력 프로세스(컨테이너 형태)를 지원하도록 설계됨
    - 파드 내부의 컨테이너들은 클러스터 내의 동일한 물리 또는 가상 머신에 자동으로 함께 배치 및 스케줄링 됨
    - 이들은 리소스와 의존성을 공유하고, 서로 통신할 수 있으며, 종료되는 시점과 방식을 조율할 수 있음
- 다중 컨테이너 구조의 좋은 예로, 한 컨테이너는 공유 볼륨에 저장된 파일을 대중에게 제공하는 웹 서버 역할을 하고, 별도의 사이드카(Sidecar) 컨테이너가 원격 소스에서 해당 파일들을 주기적으로 새로 고치거나 업데이트하는 방식을 들 수 있음
- 일부 파드는 애플리케이션 컨테이너 외에도 초기화 컨테이너(Init containers)를 가짐
    - 기본적으로 초기화 컨테이너는 애플리케이션 컨테이너가 시작되기 전에 실행을 완료해야 함
- `SidecarContainers` 기능 게이트 덕분에 초기화 컨테이너에 `restartPolicy: Always`를 지정할 수 있음
    - 이 정책이 설정된 초기화 컨테이너는 사이드카 컨테이너로 취급되어 파드의 전체 생명주기 동안 계속 실행 상태를 유지함
    - 이 사이드카 컨테이너들은 메인 애플리케이션 파드보다 먼저 시작되며, 파드가 종료될 때까지 실행을 유지하며 보조 서비스(예: 서비스 메시)를 제공함

## 컨테이너 프로브(Container probes)

- 프로브(Probe)는 컨테이너에 대해 `kubelet`이 주기적으로 수행하는 진단 작업임
- 진단을 수행하기 위해 `kubelet`은 다음과 같은 세 가지 액션을 호출할 수 있음
    - `ExecAction`: 컨테이너 런타임의 도움을 받아 수행
    - `TCPSocketAction`: `kubelet`이 직접 체크
    - `HTTPGetAction`: `kubelet`이 직접 체크
