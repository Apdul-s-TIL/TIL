# ReplicaSets

## ReplicaSet(레플리카셋)이란?

- 레플리카셋의 목적은 지정된 수의 동일한 파드(Pod) 복제본이 언제나 안정적으로 실행되도록 유지하는 것임
- 일반적으로 레플리카셋을 직접 정의하기보다 디플로이먼트를 정의하여 레플리카셋을 자동으로 관리하도록 설정함

## 레플리카셋의 작동 방식

- 레플리카셋은 다음과 같은 필드들로 정의됨
  - 셀렉터(Selector): 자신이 관리할 파드를 식별하는 기준
  - 레플리카 개수(Replicas): 유지해야 하는 파드 개수
  - 파드 템플릿(Pod Template): 레플리카 수 유지를 위해 생성하는 신규 파드에 대한 데이터를 명시
- 레플리카셋은 필드에 지정된 설정을 충족하기 위해 필요한 만큼 파드를 만들고 삭제함
- 새 파드를 생성해야 할 때는 정의된 파드 템플릿을 사용함

### 소유권 및 식별 메커니즘

- 레플리카셋은 파드의 `metadata.ownerReferences` 필드를 통해 관리 대상 파드들과 연결됨
- 레플리카셋이 가지고 있는 모든 파드의 `ownerReferences` 필드는 해당 파드를 소유한 레플리카셋을 식별하기 위한 소유자 정보를 가짐
  - 레플리카셋은 이 링크를 통해 파드의 상태를 확인하고 스케줄링을 계획함
- 레플리카셋은 셀렉터를 이용해서 새롭게 소유할 파드를 탐색함
  - 레플리카셋은 다음과 같은 조건에 해당하는 파드들이 있다면, 즉시 해당 파드를 자신의 관리 대상으로 포함함
    - 소유자 참조(ownerReference)가 없는 파드
    - 소유자가 컨트롤러가 아닌 파드 중에서 셀렉터 조건과 일치하는 파드

## 레플리카셋을 언제 사용하는가?(레플리카셋을 사용하는 시기)

- 레플리카셋은 지정된 수의 파드 레플리카가 항상 실행되도록 보장함
  - 디플로이먼트는 레플리카셋을 관리하면서 파드에 대한 선언적 업데이트(Declarative updates) 및 기타 다양한 기능을 제공하는 상위 개념임
  - 따라서 별도의 사용자 정의(custom) 업데이트 오케스트레이션이 필요하거나, 업데이트 기능 자체가 전혀 필요 없는 경우를 제외하고는, 레플리카셋을 직접 사용하는 대신 디플로이먼트를 사용하는 것을 강력히 권장함
    - 이는 실제 운영 환경에서 레플리카셋 오브젝트를 직접 조작할 일이 거의 없음을 의미하며, 대신 디플로이먼트의 `spec` 섹션에 애플리케이션을 정의하면 됨

## 템플릿 외 파드의 자동 수용(Non-Template Pod acquisitions)

- 독립적인 단일 파드(Bare Pod)를 생성할 수는 있지만, 해당 파드가 기존 레플리카셋의 셀렉터와 일치하는 레이블을 가지지 않는 것을 강력하게 권장함
  - 레플리카셋은 자신의 템플릿으로 만든 파드 외에도 셀렉터가 일치하고 소유자가 없는 파드를 자동으로 소유권에 포함시키기 때문임

### 시나리오 예시

- 상황 1: 레플리카셋 실행 중 독립 파드 추가 생성
  - 레플리카셋(원하는 수: 3개)이 이미 정상 실행 중인 상태에서 셀렉터가 일치하는 독립 파드 2개를 새로 생성하면 레플리카셋이 이 파드들을 즉시 소유권에 포함함
  - 하지만, 원하는 파드 수(3개)를 초과하게 되므로 새로 들어온 파드들은 즉시 종료(Terminating) 처리됨
- 상황 2: 독립 파드가 존재하는 상태에서 레플리카셋 생성
  - 셀렉터가 일치하는 독립 파드 2개가 먼저 실행 중인 상태에서 레플리카셋(원하는 수: 3개)을 생성하면, 레플리카셋은 기존 파드 2개를 자신의 레플리카로 수용하고 부족한 1개의 파드만 새로 생성함
- 이러한 특성 때문에 레플리카셋은 서로 다른 이미지나 설정을 가진 이종(Non-homogeneous) 형태의 파드들을 관리하게 될 수도 있음

## 레플리카셋 매니페스트 작성법

- 다른 쿠버네티스 API 오브젝트와 마찬가지로 `apiVersion`, `kind`, `metadata` 필드가 필요함
  - `kind`는 항상 `ReplicaSet`임
- 파드 이름은 레플리카셋의 `.metadata.name`을 기반으로 생성되며, 호환성을 위해 DNS 레이블 규칙을 따르는 이름(DNS 서브도메인 이름)이어야 함

### 파드 템플릿(`.sepc.template`)

- 파드 템플릿 내의 레이블(`.spec.template.metadata.labels`)은 `.spec.selector`와 반드시 일치해야 하며, 그렇지 않으면 API 서버에서 거부됨
  - 동일한 `.spec.selector`를 가지지만 파드 템플릿 사양이 서로 다른 2개의 레플리카셋이 존재할 경우, 각 레플리카셋은 상대방이 생성한 파드를 무시함
  - 다른 컨트롤러의 셀렉터와 겹치지 않도록 주의해야 함
- 템플릿의 재시작 정책 필드인 `.spec.template.spec.restartPolicy`는 오직 `Always`(기본값)만 허용됨

### 파드 셀렉터(`.spec.selector`)

- `.spec.selector` 필드는 레이블 셀렉터로 이 레이블은 소유될 가능성이 있는 파드(관리 대상 파드)를 식별하는데 사용됨

### 레플리카(`.spec.replicas`)

- `.spec.replicas`를 설정해서 동시에 동작하는 파드의 수를 지정할 수 있음
- 레플리카셋은 파드의 수가 일치하도록 생성 및 삭제함
- 기본값은 1임

## 레플리카셋 사용법

### 레플리카셋과 해당 파드 삭제

- `kubectl delete`를 사용해 레플리카셋을 삭제하면 기본적으로 레플리카셋에 종속된 모든 파드도 백그라운드 가비지 컬렉션에 의해 함께 삭제됨

### 레플리카셋만 삭제하기

- `kubectl delete`는 `--cascade=orphan` 옵션을 사용하면 파드를 남겨둔 채 레플리카셋만 삭제할 수 있음
  - 이후 동일한 셀렉터를 가진 새 레플리카셋을 생성하면, 새 레플리카셋이 남겨진 기존 파드들의 소유권을 그대로 물려받음
  - 단, 기존 파드를 새로운 템플릿 사양에 맞게 변경해 주지는 않으므로, 제어된 업데이트가 필요할 때는 레플리카셋이 아닌 디플로이먼트를 사용해야 함
    - 이는 레플리카셋이 롤링 업데이트를 직접적으로 지원하지 않기 때문임

### 종류 중인 파드 추적

- 삭제나 스케일 다운으로 인해 종료 중인 파드는 정리될 때까지 리소스를 계속 소비할 수 있음
  - 이로 인해 전체 파드 수가 일시적으로 `.spec.replicas` 설정값을 초과할 수 있음
  - 이는 레플리카의 `.status.terminatingReplicas` 필드를 통해 종료 진행 상태를 추적할 수 있음

### 레플리카셋에서 파드 격리

- 실행 중인 파드의 레이블을 변경하면 해당 파드를 레플리카셋의 관리 대상에서 제외할 수 있음
  - 디버깅이나 데이터 복구 등을 위해 특정 파드를 서비스에서 이탈시킬 때 유용함
  - 레플리카셋은 즉시 대체할 새로운 파드를 자동으로 생성함

### 레플리카셋 스케일링(Scaling)

- `.spec.replicas` 필드를 수정하여 파드 개수를 늘리거나 줄일 수 있음
- 스케일 다운(축소) 시, 파드 삭제 우선순위
  1. `Pending`(대기 중) 및 스케줄링 불가능한 파드를 가장 먼저 삭제
  2. `controller.kubernetes.io/pod-deletion-cost` 어노테이션이 설정된 경우, 값이 더 작은 파드를 먼저 삭제
  3. 파드가 더 많이 배치된 노드의 파드를 우선 삭제
  4. 생성 시간이 서로 다른 경우, 최근에 생성된 파드를 먼저 삭제(Integer log scale 단위로 계산)
  5. 위의 모든 조건이 동일하다면 무작위(Random) 선택

### 파드 삭제 비용

- 파드에 `controller.kubernetes.io/pod-deletion-cost` 어노테이션을 설정하여 스케일 다운 시 삭제될 우선순위를 지정할 수 있음
  - 범위: -214783648 ~ 214748647(기본값: 0, 음수 허용)
  - 원리: 삭제 비용 값이 낮은 파드가 값이 높은 파드보다 먼저 삭제됨
  - 유스케이스: 애플리케이션 리소스 사용률이 서로 다를 때, 축소 시 사용률이 낮은 파드가 먼저 삭제되도록 조정할 수 있음
    - e.g. Spark 배포의 드라이버 파드가 스케일 다운을 직접 제어하는 경우

### 레플리카셋을 HPA(Horizontal Pod Autoscaler)의 대상으로 설정

- 레플리카셋은 HPA의 오토스케일링 대상이 될 수 있음

## 레플리카셋의 대안(Alternatives)

### Deployment(권장사항)

- 디플로이먼트는 레플리카셋을 소유하거나 업데이트를 하고, 파드의 선언적인 업데이트와 서버측 롤링 업데이트를 할 수 있는 오브젝트임
- 레플리카셋을 단독으로 사용할 수 있지만, 오늘날에는 주로 디플로이먼트로 파드의 생성과 삭제 그리고 업데이트를 오케스트레이션하는 메커니즘을 사용함
- 디플로이먼트를 이용해서 배포할 때는 생성되는 레플리카셋을 관리하는 것에 대해 걱정하지 않아도 됨
  - 디플로이먼트는 레플리카셋을 소유하거나 관리함
  - 따라서 레플리카셋을 원한다면 디플로이먼트를 사용하는 것을 권장함

### 기본 파드(독립 파드, Bare Pods)

- 사용자가 직접 만든 파드와 달리, 레플리카셋은 노드 장애 또는 노드의 커널 업그레이드와 같은 관리 목적의 중단 등 어떤 이유로든 종료되거나 삭제된 파드를 자동으로 교체함
  - 이런 이유로 애플리에키션이 단일 파드가 필요하더라도 레플리카셋을 이용하는 것을 권장함
- 레플리카셋을 프로세스 관리자와 비교해서 생각해본다면, 레플리카셋은 단일 노드에서 개별 프로세스들이 아닌 다수의 노드에 걸쳐 있는 다수의 파드를 관리하는 것임
- 레플리카셋은 로컬 컨테이너의 재시작을 노드에 있는 kubelet과 같은 에이전트에게 위임함

### Job

- 배치 작업처럼 스스로 실행을 완료하고 종료되어야 하는 파드에는 레플리카셋 대신 Job(잡)을 사용해야 함

### DaemonSet

- 머신 모니터링 또는 머신 로깅과 같은 머신-레벨의 기능을 제공하는 파드를 위해서는 레플리카셋 대신 DaemonSet(데몬셋)을 사용해야 함
  - 이러한 파드의 수명은 머신의 수명과 연관되어 있고, 머신에서 다른 파드가 시작하기 전에 실행되어야 함
  - 머신의 재부팅/종료가 준비되었을 때, 해당 파드를 종료하는 것이 안전함

### ReplicationController

- 레플리카셋의 구버전 레거시 리소스임
- 레플리카셋은 집합 기반(Set-based) 셀렉터를 지원하므로 ReplicationController보다 선호됨
