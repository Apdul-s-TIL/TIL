# Service, Load Balancing, and Networking

## 쿠버네티스 네트워크 모델(The Kubernetes network model)

- 쿠버네티스 네트워크 모델은 다음과 같은 여러 요소로 구성됨

### 클러스터 범위의 고유 IP

- 클러스터 내의 각 파드는 클러스터 전체에서 고유한 자신만의 IP 주소가 할당됨

### 공유 네트워크 네임스페이스

- 파드는 독립된 전용 네트워크 네임스페이스를 가짐
  - 이 네임스페이스는 파드 내부의 모든 컨테이너가 공유함
    - 따라서 동일한 파드에 속한 서로 다른 컨테이너에서 실행되는 프로세스들은 `localhost`를 통해 서로 통신할 수 있음

### 파드 네트워크(클러스터 네트워크)

- 파드 네트워크는 파드 간의 통신을 처리함
- 파드 네트워크는 의도적인 네트워크 격리(Segmentation)가 적용되어 있지 않다면 다음과 같은 원칙을 보장함
  - 모든 파드는 서로 동일한 노드에 있든, 다른 노드에 있든 관계없이 다른 모든 파드와 통신할 수 있음
  - 파드들은 프록시(Proxy)나 주소 변환(NAT)을 거치지 않고 직접 통신함
    - 단, Windows 환경의 Host-network 파드에는 이 규칙이 적용되지 않음
  - 노드에서 실행되는 에이전트(시스템 데몬 또는 `kubelet` 등)는 해당 노드에 있는 모든 파드와 통신할 수 있음

### 서비스(Service) API

- 서비스 API를 사용하면 하나 이상의 백엔드 파드가 제공하는 서비스에 안정적이고 지속적인(Long-lived) IP 주소나 호스트네임을 제공할 수 있음
  - 이 때 서비스를 구성하는 개별 파드는 시간이 지남에 따라 변경될 수 있음

### 엔드포인트슬라이스(EndpointSlice)

- 쿠버네티스는 현재 서비스를 지원하고 있는 파드들에 관한 정보를 제공하기 위해 엔드포인트슬라이스(EndpointSlice) 오브젝트를 자동으로 관리함

### 서비스 프록시(Service Proxy)

- 서비스 프록시 구현체는 Service 및 EndpointSlice 오브젝트의 집합을 모니터링하고, 운영체제나 클라우드 제공자의 API를 사용하여 패킷을 가로채거나 재작성함으로써 서비스 트래픽이 올바른 백엔드로 라우팅되도록 데이터 플레인을 프로그래밍함

### 게이트웨이(Gateway) API 및 이전 버전의 Ingress

- 클러스터 외부에 있는 클라이언트가 클러스터 내부의 서비스에 접근할 수 있도록 해 줌
- LoadBalancer 타입 서비스
  - 해당 서비스가 지원되는 클라우드 공급자를 사용하는 경우, Service API의 `type: LoadBalancer`를 통해 보다 간단하게(다만 설정 자유도는 낮은) 클러스터 수신(Ingress) 메커니즘을 구성할 수 있음

### 네트워크 정책(NetworkPolicy, 네트워크폴리시)

- 파드 간 트래픽이나 파드와 외부 환경 간 트래픽을 제어할 수 있게 해주는 쿠버네티스 내장 API임

## 기존 컨테이너 시스템과의 차이점

- 이전의 컨테이너 시스템에서는 서로 다른 호스트에 있는 컨터이너 간 연결이 자동으로 제공되지 않았음
  - 그래서 서로 다른 호스트 컨테이너 간 링크를 명시적으로 만들거나, 다른 호스트의 컨테이너가 접근할 수 있도록 컨테이너 포트를 호스트 포트에 매핑해야 하는 경우가 많았음
- 쿠버네티스에서는 위 작업이 필요하지 않음
  - 쿠버네티스 모델에서는 포트 할당, 명명(Naming), 서비스 디스커버리, 로드 밸런싱, 애플리케이션 구성 및 마이그레이션 관점에서 파드를 마치 가상 머신(VM)이나 물리 호스트처럼 다룰 수 있도록 지원함

### 구성 요소 구현 방식(외부 컴포넌트와 역할 분담)

- 이 네트워크 모델 중 쿠버네티스 자체가 직접 구현하는 부분은 일부에 불과함
- 쿠버네티스는 표준 API를 정의하고, 실제 기능은 외부 컴포넌트(일부는 선택 사항)가 제공함
- 파드 네트워크 네임스페이스 설정
  - 컨테이너 런타임 인터페이스(CRI, Container Runtime Interface)를 구현하는 시스템 레벨의 소프트웨어가 담당함
- 파드 네트워크 자체 관리
  - 파드 네트워크 구현체가 담당함
  - 리눅스 환경에서 대부분의 컨테이너 런타임은 CNI(Container Networking Interface)를 사용하여 파드 네트워크 구현체와 상호작용함
    - 이러한 구현체를 보통 CNI 플러그인이라고 부름
- 서비스 프록시 구현
  - 쿠버네티스는 `kube-proxy`라는 기본 서비스 프록시 구현체를 제공함
  - 하지만, 일부 파드 네트워크 구현체는 성능 향상과 긴밀한 통합을 위해 자체적인 서비스 프록시를 대신 사용하기도 함
- 네트워크 정책(NetworkPolicy, 네트워크폴리시)
  - 일반적으로 파드 네트워크 구현체(CNI)에 의해 구현됨
    - 단순한 네트워크 구현체 중에는 NetworkPolicy를 지원하지 않는  경우도 있음
    - 관리자가 NetworkPolicy 지원 없이 구성할 수 있음
    - 이 경우 API 자체는 존재하지만 실제 적용되지는 않음
- 게이트웨이(Gateway) API
  - 매우 다양한 구현체가 존재함
    - 특정 클라우드 환경 전용 구현체, 베어메탈(Bare metal) 환경에 특화된 구현체, 혹은 포괄적인 범용 구현체 등이 있음
